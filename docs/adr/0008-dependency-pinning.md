# 0008. Backend dependencies are resolved from pyproject, not a committed lock file

**Status:** accepted — 2026-09-11

## Context

The initial plan was to commit an exact-pinned `requirements.lock` generated by
`pip freeze`, so that builds were reproducible.

That lock was generated on Windows, and it was wrong for the deployment target in both
directions:

- It pinned `pywin32`, which has no Linux distribution at all. The image build failed
  outright.
- It **omitted** `uvloop` and `httptools`. Those come from `uvicorn[standard]` and are not
  installed on Windows, so `pip freeze` never saw them. Because the Dockerfile then ran
  `pip install --no-deps -e .`, the Linux image would have silently run uvicorn without
  its high-performance event loop -- a failure that produces no error, just worse
  behaviour.

The second problem is the dangerous one: the first fails loudly, the second does not.

Hand-editing environment markers into the lock was rejected: the correct Linux versions of
packages this machine never resolved would have to be invented, and inventing versions is
the same class of error as inventing metrics.

## Decision

The image installs from `pyproject.toml`, whose version floors express real API
requirements. No lock file is committed.

CI records `pip freeze` **on Linux**, after a real resolution on the deployment platform,
and publishes it as the `build-record` artifact alongside coverage. That is a truthful
record of what was installed rather than an aspirational input that was never validated.

## Consequences

- Builds are not byte-reproducible across time; a new patch release of a dependency can
  enter a rebuild. Accepted for now, and revisited when a Linux-generated lock can be
  produced on the deployment platform (a `pip-compile` or `uv lock` step in CI).
- Constraint C5 is not weakened. C5 is about reproducing *scan results*, which depend on
  the **analysis tool** versions -- and those live in the sandbox image, are exactly
  pinned there in phase 2, and are recorded per scan in `scans.tool_versions`
  (see ADR 0003). The web framework version does not change what an analyser reports.
- A developer on Windows and CI on Linux can resolve slightly different versions. The CI
  resolution is the authoritative one, since it matches production.
